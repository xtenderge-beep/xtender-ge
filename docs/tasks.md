## Протокол — обязательно для каждой новой сессии

Не важно, какой инструмент/модель работает с этим репозиторием (Claude Code,
другая среда, другой человек) — правила одни:

1. **Перед началом любой работы** прочитайте этот файл целиком, не только
   заголовки. Задача может быть заблокирована, частично сделана или отменена —
   это видно только из заметки внутри неё.
2. Если пользователь не указал конкретную задачу — берите первую невыполненную
   не в блоке «Выполнено» сверху вниз.
3. **Сразу после того как задача сделана** — отметьте её здесь же (`[x]`,
   дата, коммит, короткий итог) и переместите в раздел «Выполнено». Не
   откладывайте это на «потом» и не полагайтесь на память модели — если
   сессия прервётся до этого шага, следующая сессия увидит задачу как
   невыполненную и может повторить работу или потерять контекст.
4. Если задача оказалась не такой, как описана (сделали иначе / решили не
   делать / выяснилось, что не нужна) — не удаляйте запись, смените статус
   и опишите, что изменилось и почему. Пустая история хуже неидеальной.
5. Если для продолжения нужен ответ или решение пользователя (не техническое,
   а продуктовое/организационное) — статус `[!]`, чётко сформулируйте вопрос
   внутри задачи. Не гадать и не выполнять вместо пользователя.
6. Новую задачу — дописывайте в конец активного списка с той же структурой:
   заголовок, статус, контекст (что и почему), критерий готовности.
7. **Локальная рабочая копия может редактироваться параллельно другой
   сессией прямо сейчас** (не только через git — файлы на диске). Перед
   `git add`/коммитом смотрите `git status` и стейджите только файлы,
   которые реально относитесь к вашей задаче — не `git add -A`/`.`.
   Прецедент 2026-09-15: во время работы над задачей ниже про телефон в
   рабочей копии обнаружились чужие незакоммиченные правки (`i18n.js`,
   `index.ejs`, `input.css` — карусель примеров на главной) и отдельный уже
   запушенный коммит `ecdc6c1` от другой сессии — оба не имели отношения к
   текущей задаче, тронуты не были.

**Легенда статусов**: `[ ]` не начато · `[~]` в процессе (см. заметку, где
остановились) · `[!]` заблокировано (см. заметку, чего ждём) · `[x]` сделано

поле IBAN в блоке реквизитов. Если там `GE22BG...318` — заменить на
`GE95BG0000000613339218` прямо в форме (без деплоя кода). Если уже верное —
просто отметить задачу выполненной с пометкой «уже было верно».

### [ ] Вход мастера — восстановить нормализацию телефона

Регрессия из коммита `ae9a1c3` (2026-09-14, изменения через другую модель).
`master.controller.js` → `loginRequestCode`/`loginVerify`: раньше номер
приводился к канонической форме через `toE164()` перед поиском мастера в БД
(`masterService.getMasterByPhone`, точное сравнение `WHERE phone = $1`).
Теперь используется сырой ввод, провалидированный строгим регексом
`+995XXXXXXXXX` (`isGeorgianPhone`) — без нормализации. Раньше номер без `+`
или без кода страны (`995...`, просто 9 цифр) успешно находил мастера; теперь
такой ввод отклоняется как «не грузинский номер», даже если после
нормализации он оказался бы тем же самым зарегистрированным номером.

Живой тест на dev-server (2026-09-15) подтвердил: `+995510000000` входит,
`995510000000` и `510000000` (тот же номер без форматирования) — нет.

Поля логина на сайте подставляют `+995` заранее и валидируют формат на
клиенте, поэтому обычный вход через сайт не задет. Риск — автозаполнение
браузером/менеджером паролей старым сохранённым форматом номера, либо
сторонние клиенты API.

Не чинили: не совпадало с поломкой, которую в той сессии искал пользователь
(это был краш-луп миграции, см. «Выполнено» ниже).

**Критерий готовности**: `loginRequestCode`/`loginVerify` снова нормализуют
номер через `toE164()` перед `getMasterByPhone`, сохраняя при этом
Georgian-only проверку формата ПОСЛЕ нормализации (не до) — так, чтобы
`995...`/`510000000`/`+995 510 000 000` находили того же мастера, что и
`+995510000000`. Добавить кейс в `tests/georgian-phone.test.js` или новый
тест, воспроизводящий сценарий из живой проверки выше.

### [!] Риск двойного зачисления: Telegram-бот `/topup` не знает о счетах

Обнаружено 2026-09-16 при обсуждении с владельцем сверки выписки на `/admin/receipts`
(см. `current-state.md`, раздел «Сверка пополнений...»). `order.controller.js` →
`applyTopUp` (команда `/topup <телефон> <сумма>` в Telegram) зачисляет баланс напрямую
через `masterService.topUpBalance()`, минуя `topup_requests` и `bank_statement_credits`.

Если модератор зачислит реальный перевод этой командой, а тот же перевод затем попадёт
в загруженную банковскую выписку и будет вручную привязан к какому-то счёту на
`/admin/receipts` (или наоборот — сначала привязка, потом бот) — один и тот же реальный
перевод зачислится дважды. Раньше это было маловероятно (старая `/admin/receipts` только
помечала статус чека и не двигала баланс сама); после сегодняшних изменений кнопки на
этой странице стали полноценным альтернативным путём зачисления, так что риск стал
реальным. Дедупликация по номеру документа банка (`bank_statement_credits`) защищает
только от повторной обработки ОДНОЙ И ТОЙ ЖЕ выписки — она не знает о зачислениях,
сделанных через Telegram-бота.

Нужно решение владельца, не техническое: (а) перестать использовать Telegram-`/topup`
для платежей, у которых уже есть созданный счёт с номером в назначении, оставив бота
только для случаев без счёта, или (б) при зачислении через бота проверять, не похож ли
телефон+сумма на уже существующий неоплаченный счёт, и предупреждать модератора.

**Критерий готовности**: решение зафиксировано (выбран вариант, либо риск сознательно
принят с описанием почему) — при необходимости реализовано и покрыто тестом.
