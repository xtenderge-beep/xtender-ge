# Автоперевод текста заявки

Заказчик пишет заявку на своём языке → машинный перевод → исполнитель на `/order/<token>`
читает на своём, модератор в Telegram — на русском.

**Включение:** переменная `OPENROUTER_API_KEY` в Railway (ключ с openrouter.ai, оплата по
факту). Без ключа сервис работает вхолостую — заявки создаются как раньше, везде
показывается оригинал.

---

## 1. Как работает

1. Клиент пишет заявку, подтверждает SMS-кодом.
2. **В фоне** (ответ клиенту не ждёт): `translation.service.translateOrder(description)`
   определяет язык оригинала по алфавиту (грузинский → `ka`, кириллица → `ru`, иначе
   `en`) и переводит на два других языка **параллельно**. Общий таймаут 7 с.
3. Результат → `orders.description_translations` (JSONB `{ru: "...", en: "..."}`) +
   `orders.source_lang`. `orders.description` не трогаем — это оригинал заказчика.
4. Сразу после — `telegram.notifyModerator(order)` с уже подставленным переводом.
5. **Сбой/таймаут/нет ключа** → заявка и рассылка идут дальше с оригиналом. Перевод
   никогда не блокирует создание заказа. Перевод одного языка не роняет второй.

Перевод делается **один раз при создании заявки**, не при каждом открытии. 10 исполнителей
открыли лид → вызов перевода был один, текст уже в базе.

## 2. Что видит исполнитель на `/order/<token>`

- Текст заявки **на языке страницы** (кука `lang`), если перевод есть — иначе оригинал.
- Бейдж **«🌐 переведено»** + сворачиваемый блок **«Показать оригинал»**.
- Кнопка **«Копировать»** — всегда копирует **оригинал** (чтобы кинуть в свой переводчик).
- Кнопка **WhatsApp** ведёт на `wa.me/<номер>?text=...` с заготовкой: приветствие на
  языке заказчика (`order_wa_template`, `source_lang`) + текст заявки в оригинале.
- Строка-подсказка **«Заказчик пишет на другом языке — удобнее в WhatsApp»** — когда
  `source_lang` ≠ язык страницы.

## 3. Что видит модератор в Telegram

`telegram.service.moderatorDescription(order)`: если `source_lang` ≠ `ru` и есть `ru`
перевод → русский текст + строка `🔤 оригинал (<lang>): <оригинал>`. Иначе просто оригинал.
Используется и в `notifyModerator`, и в `buildMessageText` (перестройка сообщения при
обновлении воронки).

## 4. Движок и модель

- OpenRouter, OpenAI-совместимый `/chat/completions`.
- Модель по умолчанию **`google/gemini-2.5-flash-lite`** — выбрана бенчмарком (см.
  `HANDOFF.md`, раздел про бенчмарк перевода): чисто по ka/ru/en, ~0.6 с, **~$0.14 за
  1000 заявок** (заявка = 2 перевода). Переопределяется `OPENROUTER_TRANSLATION_MODEL`.
- Промпт (`translation.service.buildPrompt`): жёсткие правила «адреса/имена/числа не
  трогать, названия писать в алфавите целевого языка» + **глоссарий терминов** спецтехники
  (эвакуатор → ევაკუатორი, автовышка → ავტოამწე и т.д.). Глоссарий заметно поднял
  качество слабых мест — держать в синхроне с `serviceTypes.js`, если добавляются типы.

## 6. Не переведено (осознанно)

- `/o/<owner_token>` — страница заказчика: он сам писал заявку, поэтому видит **оригинал**
  (перевод + бейдж «переведено» только у не-владельца — `!isOwner` в `order.ejs`).
  `showByOwnerToken` рендерит страницу на `order.source_lang` (заказчик пришёл из SMS,
  куки языка у него нет — иначе была бы дефолтная ka).
- `my-orders`, SMS.
- `district_name` в заявке — свободный текст, останется как ввёл клиент (районы станут
  структурными в рамках `docs/service-types.md`).
- Telegram-лид **исполнителю** (не модератору) — оригинал; перевод исполнитель видит по
  ссылке на `/order/<token>`.

## 7. pg-mem

Хранение/чтение JSONB работает (возвращается распарсенным объектом). Проверено сквозным
тестом на dev-server: заявка на грузинском → перевод сохранён → `/order` отдаёт русский
текст + бейдж + WhatsApp-заготовку.
