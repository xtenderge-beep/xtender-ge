# Типы услуг исполнителей — конфиг-движок

Справочник по подсистеме «какие услуги оказывают исполнители» (`van`, `movers`, `tow`,
`bucket_lift`, дальше — спецтехника): как устроено, как добавить новый тип, что уже
работает и что нет.

Повод: старая модель (`masters.category` = 2 значения + приклеенные булевы
`vehicle_size` / `is_flatbed`) не расширялась. Владелец планирует эвакуаторы, автовышки,
манипуляторы. Решение — один конфиг-файл, из которого генерируется вся обвязка.

---

## 1. Архитектура

**Три слоя:**

1. **`master_services`** (таблица) — `master_id`, `service_type`, `attributes` (JSONB),
   `is_primary`. Один исполнитель = N услуг (пока регистрация заводит одну).
2. **`attributes`** — характеристики, специфичные для типа (размер кузова, тип погрузки,
   тоннаж, высота стрелы…). Ключи и правила матчинга описаны в конфиге.
3. **`src/config/serviceTypes.js`** — единственный источник правды. Из него генерируются:
   форма `/join`, группы и фильтры каталога, бейджи карточек, навигация и чипы на
   главной, schema.org. (Рассылка в Telegram и админка — Фазы 4–5.)

**Локация:** `cities` (пока активен только Тбилиси) + `districts` (+`city_id`, локали,
`slug`) + `master_districts` (где исполнитель берёт заказы) + `masters.city_id` +
`orders.city_id`.

**Фильтрация по `attributes` — в JS**, не в SQL: pg-mem (локальная разработка,
`dev-server.js`) не тянет JSONB-операторы. Пул исполнителей на тип маленький, JS-фильтр
на нём дёшев. См. `master.service.listMasters` — тип и attributes подтягиваются вторым
запросом и клеятся в JS.

## 2. Конфиг `src/config/serviceTypes.js`

```js
const SERVICE_TYPES = {
  <type>: {
    icon: '🚚',
    catalogGroup: true,                 // показывать группой в каталоге
    catalogColor: 'bg-amber-100 …',      // классы бейджа группы
    fields: [ <field>, … ],
  },
};
const SERVICE_TYPE_ORDER = ['van', 'movers', 'tow', 'bucket_lift'];  // порядок в UI
```

**Поле (`field`):**

| ключ | значение |
|---|---|
| `key` | ключ в `master_services.attributes` и в атрибутах заявки |
| `input` | `enum` \| `number` \| `bool` \| `size` — как рисовать на форме |
| `options` | для `enum`/`size` — **по возрастанию значимости** (`match:'gte'` смотрит порядок) |
| `optionIcons` | `{ value: 'fa-…' }` — иконки к вариантам enum (напр. кузов) |
| `unit` | суффикс для `number` (`'м'`, `'т'`, `'чел.'`) |
| `min`, `max` | границы для `number` |
| `match` | как матчить требование клиента с атрибутом исполнителя (см. ниже) |
| `filter` | `true` → фильтр в каталоге + кнопка в рассылке модератору |
| `required` | `true` → обязательное поле при регистрации |

**`match` (используется Фазой 4):**

- `exact` — `attr === запрос` (тип кузова, тип погрузки)
- `gte` — `attr >= запрос`; для enum сравнение по индексу в `options`
- `flag` — клиент просит `true` → нужен `true` у исполнителя; иначе не фильтруем (гидроборт)
- `ignore` — на форме есть, в матчинге не участвует

**`input: 'size'`** — особый: система выводит тир из габаритов кузова.
`deriveVanSize(l, w, h, sizes)` теперь (с 2026-09-16) считает не по объёму, а по тем же
per-измерению минимумам, что использует сам тариф «Грузовой» Яндекса: тир присваивается,
только если длина **И** ширина **И** высота одновременно не меньше его порога (проверка
от XXL вниз, первый подходящий побеждает) — узкое/низкое измерение утягивает вниз всю
категорию, даже если остальные два больше нормы.

| тир | длина от | ширина от | высота от |
|---|---|---|---|
| S | 170 см | 100 см | 90 см |
| M | 260 см | 130 см | 150 см |
| L | 380 см | 180 см | 180 см |
| XL | 400 см | 190 см | 200 см |
| XXL | 500 см | 200 см | 200 см |

Пустые габариты → `null` = «любой размер». **Пороги теперь настраиваются из админки без
деплоя**: `settings.service.getVanSizeThresholds()`/`setVanSizeThresholds()` — новый ключ
`van_size_thresholds` в общей таблице `app_settings` (тот же паттерн, что цена лида и
приветственный бонус), с фолбэком на дефолты выше, пока админ ничего не сохранил. Форма —
`/admin/categories/van`, блок «Размер кузова» (3 числовых поля см на каждую букву).
Буквы S/M/L/XL/XXL сами остаются фиксированы в коде — на них завязаны CHECK-констрейнты
`masters_vehicle_size_check`/`order_dispatches_vehicle_size_check` в `schema.sql` и
несколько `ALLOWED_SIZES`-множеств в контроллерах; настраиваются только см-пороги за
каждой буквой, не набор самих букв.

**Живой ввод в `/manager/review/:id` (карточка быстрого одобрения модератора)**:
менеджер вводит длину/ширину/высоту кузова в см (как написано у исполнителя в описании),
`deriveVanSize` определяет букву на сервере (клиентский JS в `review.ejs` только
показывает превью по тем же порогам, не участвует в записи). Чекбокс «точные размеры
неизвестны» — эквивалент прежнего пункта «любой размер», отключает поля см и шлёт
`vehicleSize=any`. То же есть в `/admin/masters/:id` — там по-прежнему прямой выбор буквы
(с см-подсказкой рядом), без автоопределения по трём числам.

**Экспортируемые хелперы:** `validateAttributes(type, raw)` (коэрция+валидация ввода
формы), `legacyColumnsFor(type, attrs)` (синк старых колонок), `configForView(t)` /
`catalogGroupsForView(t)` / `attributeBadges(type, attrs, t)` (разворот для EJS).

## 3. Действующие типы

| тип | иконка | поля | комментарий |
|---|---|---|---|
| `van` — Перевозки | 🚚 | размер (S/M/L/XL/XXL, см. выше), кузов (закрытый/борт), ☐ гидроборт, ☐ с грузчиками | единственная категория с локальным полем `size` — характеристики (кроме него) редактируются в `/admin/categories/van` как у любой другой с 2026-09-16 |
| `movers` — Грузчики | 💪 | бригада, чел. | «мешками» (вывоз мусора вручную, без техники) сюда же — отдельная категория для этого заводилась и была убрана 2026-09-16 как дублирующая |
| `junk` — Вывоз мусора (самосвал) | 🧹 | объём кузова (до 2 / 4 / 8 / 15+ м³) | добавлено 2026-09-16 — раньше было 0 характеристик; НЕ то же самое, что `van` с `body:flatbed` (у самосвала кузов опрокидывается, у бортового — нет) |
| `tow` — Эвакуатор | 🛻 | тип погрузки (ломаная платформа / паук), макс. тоннаж (до 3.5 / до 8 / 20+ т) | пороги тоннажа — дефолт, владелец подтвердит |
| `bucket_lift` — Автовышка (жираф) | 🏗️ | рабочая высота (8–60 м), тип стрелы (телескоп / коленчатая) | ≠ манипулятор (КМУ, груз крюком — будет отдельным типом) |

## 4. i18n — конвенция ключей

Все в `ka/ru/en` (`src/config/i18n.js`):

```
svc_<type>                      — название типа        («Эвакуатор»)
svc_<type>_<fieldKey>           — подпись поля          («Тип погрузки»)
svc_<type>_<fieldKey>_<value>   — подпись варианта enum («Паук (частичная погрузка)»)
service_desc_<type>_body        — описание в блоке «услуги» на главной
chip_<type>                     — чип «что нужно сделать» (только tow/bucket_lift; у van/movers свои chip_move/chip_movers)
```

Если ключа варианта enum нет — фолбэк на `value + unit` (напр. тоннаж `«8 т»`), поэтому
для числовых enum-опций подписи необязательны.

---

## 5. Как добавить новый тип (напр. `manipulator` — КМУ)

1. Блок в `SERVICE_TYPES` (`src/config/serviceTypes.js`) + добавить в `SERVICE_TYPE_ORDER`.
2. Строки `svc_manipulator*` + `service_desc_manipulator_body` + `chip_manipulator` в
   `i18n.js` (ka/ru/en).
3. **Всё.** Форма, каталог, фильтры, главная подхватят автоматически.
   Рассылка/админка — когда будут переведены на конфиг (Фазы 4–5).

Миграций БД не требуется — `attributes` это JSONB.

## 6. Статус по фазам (2026-09-06)

| Фаза | Что | Статус |
|---|---|---|
| 1 | Схема (`cities`, `districts`, `master_services`, `*.city_id`), конфиг, миграция существующих | ✅ |
| 2 | Форма `/join` из конфига: тип → поля + город + районы + фото | ✅ |
| 3 | Каталог + главная из конфига, спецтехника видна, группа `junk` убрана | ✅ |
| 4a | Рассылка спецтехники: кнопки модератора «Эвакуатор»/«Автовышка», dispatch работает | ✅ |
| 4b | Кнопки модератора из конфига (авто для новых типов), матчинг-движок по `attributes`, структурная форма заявки клиента (тип+город+район) | — |
| 5 | Админка из конфига; удалить старые колонки `category`/`vehicle_size`/`is_flatbed` | ◐ частично, см. ниже |

**Фаза 4a (2026-09-06):** `tow`/`bucket_lift` работают в рассылке end-to-end **без переписывания
`notifyMasters`** — потому что при регистрации `legacyColumnsFor` пишет `masters.category` =
сам тип, а старый `notifyMasters` фильтрует `AND category = $1`. Добавлено: 2 кнопки в
клавиатуру модератора (`telegram.service` `buildKeyboardWithCounts`), 2 подписи в
`CATEGORY_LABELS`, `tow`/`bucket_lift` в `ALLOWED_CATEGORIES` (`order.controller`), `S` в
`SIZE_ORDER`/`SIZE_SPECS`. Кнопка «🧹 Вывоз мусора» показывается только если остались
легаси-профили `category='junk'` (новые = «Бортовые»). Проверено E2E: заявка на эвакуатор →
модератор жмёт «🛻 Эвакуатор» → tow-мастер получает лид + списание 50 тетри.

**Поправка к 4a:** абзац выше про кнопку «🧹 Вывоз мусора» устарел — с 2026-09-16 `junk`
снова полноценная, активно используемая категория (объём кузова, см. §3), а не только
легаси-хвост старых профилей.

**Фаза 4b (не сделано):** матчинг по `attributes` (гидроборт/тоннаж/высота) — нужна
структурная форма заявки клиента, где он указывает тип+атрибуты. Сейчас клиент пишет
текстом, модератор читает и жмёт тип — рассылка идёт всем мастерам этого типа с балансом,
без фильтра по атрибутам. Правила матчинга (`match: exact/gte/flag`) в конфиге есть, движок
не написан.

**Фаза 5 (частично, 2026-09-14…2026-09-16):** админка получила реальное самостоятельное
управление конфигом категорий, но не до конца — легаси-колонки `category`/`vehicle_size`/
`is_flatbed` всё ещё существуют и активно читаются (рассылкой, каталогом), не удалены.
Сделано:
- Создание новой категории (`POST /admin/categories`, без `slug`) — работало уже на
  09-06, просто не было задокументировано здесь.
- **Удаление** категории (`POST /admin/categories/:slug/delete`) — новое 09-16.
  Заблокировано, если категорией уже пользуется хоть один специалист (проверка по
  `masters.category` и `master_services.service_type`) — иначе его профиль остался бы
  ссылаться на несуществующую категорию и сломал бы повторное одобрение/каталог/рассылку
  для него. Подсказка при блокировке — снять «Категория активна» вместо удаления.
- **Редактирование характеристик `van`** — раньше `hasLockedField()` прятал ВЕСЬ блок
  характеристик категории целиком, если у неё было поле `input==='size'` (это только
  `van`). Теперь блокируется только само поле `size` (ставится отдельной legacy-колонкой,
  см. §2) — «Тип кузова»/«Гидроборт»/«С грузчиками» у `van` редактируются в общей форме,
  как у любой другой категории.
- **См-пороги `size` из админки** — см. §2 выше (`/admin/categories/van`, блок «Размер
  кузова»). Буквы фиксированы кодом, сантиметры за ними — нет.
- **Модераторская карточка быстрого одобрения** (`/manager/review/:id`, не /admin —
  см. `docs/manager-portal.md`) — по сути мини-версия «формы из конфига» для одного,
  самого частого случая (новая регистрация, обязательные поля). Полноценная форма всех
  полей всех типов по-прежнему только в `/admin/masters/:id`.

Не сделано в Фазе 5: удаление легаси-колонок; редактирование `match`/`filter`/
`optionIcons` из UI (переносятся как есть при сохранении, см. «Выполнено» в `tasks.md`
за 09-15); создание нового поля с `input:'size'` через форму (недоступно — 'size' не
входит в разрешённые типы `parseFields`, только у `van` он есть исторически).

**Что работает сейчас:** регистрация всех 4 типов; каталог показывает группы (появляются,
когда есть одобренный исполнитель); прямой звонок из каталога (платное раскрытие номера)
для любого типа; главная рекламирует все 4 услуги.

**Что НЕ работает до Фазы 4:** заявка клиента через композер на спецтехнику доходит до
модератора **текстом**, но авто-рассылки нет — в Telegram у модератора кнопки только
`transport` / `movers` / `junk` / `flatbed` + размеры. Модератор обрабатывает эвакуатор
вручную.

**Переходный дуализм (до Фазы 5):** `van`/`movers` при регистрации пишут И
`master_services`, И старые колонки `masters.category`/`vehicle_size`/`is_flatbed` — их
ещё читает рассылка (`order.service.notifyMasters`). Для `tow`/`bucket_lift` старого
эквивалента нет: `category` = сам тип, старый каталог/рассылка их игнорируют.

## 7. Открытые вопросы

- **Пороги тоннажа эвакуатора** (3.5 / 8 / 20 т) и **высоты жирафа** (свободный ввод
  8–60 м) — мои дефолты в `serviceTypes.js`, владелец обещал сверить с рынком.
- **Грузинские `svc_*` / `service_desc_*` строки** — писал не носитель, нужна вычитка
  (как и юр.текст, см. `docs/consent-and-legal.md`). `ავტოამწე` для автовышки — вариант.
- **Выбор машины из готового списка** (Газель / Спринтер / Транзит → тир+кузов) как
  альтернатива вводу габаритов — реализовано другим путём 2026-09-16: менеджер вводит
  длину/ширину/высоту напрямую (см. §2/§6, `/manager/review/:id`), а не выбирает модель
  из справочника. Список моделей под тбилисский парк по-прежнему не составлен — если
  ввод см на практике окажется неудобным/неточным, справочник моделей остаётся
  запасным вариантом.
- **Мультиуслуга** (один исполнитель — несколько типов): таблица `master_services` это
  поддерживает, но регистрация и кабинет заводят/показывают одну.
- **Города кроме Тбилиси**: `cities` заполнена (Батуми/Кутаиси/Рустави, `is_active=false`),
  включаются флагом — но каталог/рассылка ещё не city-aware (Фаза 4).

## 8. pg-mem — чего избегать в SQL этой подсистемы

(полный список — `HANDOFF.md` + память `xtender-db-test-harness`)

- **Нет `jsonb_build_object`** — JSON собирать конкатенацией строк + `::jsonb`.
- **Коррелированный `NOT EXISTS` в `INSERT … SELECT`** падает — идемпотентность через
  `UNIQUE` + `ON CONFLICT DO NOTHING`.
- **`GROUP BY` по jsonb-колонке** — не полагаться; `listMasters` поэтому клеит attributes
  в JS вторым запросом, а не джойном.
- Хранение/чтение JSONB как таковое — работает (возвращается распарсенным объектом).
