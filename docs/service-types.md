# Типы услуг исполнителей — конфиг-движок

Справочник по подсистеме «какие услуги оказывают исполнители» (`van`, `movers`, `tow`,
`bucket_lift`, дальше — спецтехника): как устроено, как добавить новый тип, что уже
работает и что нет.

Повод: старая модель (`masters.category` = 2 значения + приклеенные булевы
`vehicle_size` / `is_flatbed`) не расширялась. Владелец планирует эвакуаторы, автовышки,
манипуляторы. Решение — один конфиг-файл, из которого генерируется вся обвязка.

---

## 1. Архитектура

**Три слоя:**

1. **`master_services`** (таблица) — `master_id`, `service_type`, `attributes` (JSONB),
   `is_primary`. Один исполнитель = N услуг (пока регистрация заводит одну).
2. **`attributes`** — характеристики, специфичные для типа (размер кузова, тип погрузки,
   тоннаж, высота стрелы…). Ключи и правила матчинга описаны в конфиге.
3. **`src/config/serviceTypes.js`** — единственный источник правды. Из него генерируются:
   форма `/join`, группы и фильтры каталога, бейджи карточек, навигация и чипы на
   главной, schema.org. (Рассылка в Telegram и админка — Фазы 4–5.)

**Локация:** `cities` (пока активен только Тбилиси) + `districts` (+`city_id`, локали,
`slug`) + `master_districts` (где исполнитель берёт заказы) + `masters.city_id` +
`orders.city_id`.

**Фильтрация по `attributes` — в JS**, не в SQL: pg-mem (локальная разработка,
`dev-server.js`) не тянет JSONB-операторы. Пул исполнителей на тип маленький, JS-фильтр
на нём дёшев. См. `master.service.listMasters` — тип и attributes подтягиваются вторым
запросом и клеятся в JS.

## 2. Конфиг `src/config/serviceTypes.js`

```js
const SERVICE_TYPES = {
  <type>: {
    icon: '🚚',
    catalogGroup: true,                 // показывать группой в каталоге
    catalogColor: 'bg-amber-100 …',      // классы бейджа группы
    fields: [ <field>, … ],
  },
};
const SERVICE_TYPE_ORDER = ['van', 'movers', 'tow', 'bucket_lift'];  // порядок в UI
```

**Поле (`field`):**

| ключ | значение |
|---|---|
| `key` | ключ в `master_services.attributes` и в атрибутах заявки |
| `input` | `enum` \| `number` \| `bool` \| `size` — как рисовать на форме |
| `options` | для `enum`/`size` — **по возрастанию значимости** (`match:'gte'` смотрит порядок) |
| `optionIcons` | `{ value: 'fa-…' }` — иконки к вариантам enum (напр. кузов) |
| `unit` | суффикс для `number` (`'м'`, `'т'`, `'чел.'`) |
| `min`, `max` | границы для `number` |
| `match` | как матчить требование клиента с атрибутом исполнителя (см. ниже) |
| `filter` | `true` → фильтр в каталоге + кнопка в рассылке модератору |
| `required` | `true` → обязательное поле при регистрации |

**`match` (используется Фазой 4):**

- `exact` — `attr === запрос` (тип кузова, тип погрузки)
- `gte` — `attr >= запрос`; для enum сравнение по индексу в `options`
- `flag` — клиент просит `true` → нужен `true` у исполнителя; иначе не фильтруем (гидроборт)
- `ignore` — на форме есть, в матчинге не участвует

**`input: 'size'`** — особый: система выводит тир из габаритов кузова.
`deriveVanSize(l, w, h)` считает объём и присваивает `S/L/XL/XXL`:

| тир | объём | пример |
|---|---|---|
| S | < 4 м³ | легковая, Berlingo, Doblo |
| L | 4–12 м³ | Transit L2H2 (≈10) |
| XL | 12–17 м³ или длина ≥ 400 см | Sprinter Maxi (≈15), Газель-тент |
| XXL | ≥ 17 м³ или длина ≥ 450 см | Газель 4м+, грузовик |

Пустые габариты → `null` = «любой размер». Пороги — первый прикид по тбилисскому парку,
правятся одним местом в `deriveVanSize`.

**Экспортируемые хелперы:** `validateAttributes(type, raw)` (коэрция+валидация ввода
формы), `legacyColumnsFor(type, attrs)` (синк старых колонок), `configForView(t)` /
`catalogGroupsForView(t)` / `attributeBadges(type, attrs, t)` (разворот для EJS).

## 3. Действующие типы

| тип | иконка | поля | комментарий |
|---|---|---|---|
| `van` — Перевозки | 🚚 | размер (авто из габаритов), кузов (закрытый/борт), ☐ гидроборт, ☐ с грузчиками | «вывоз мусора» = `body:flatbed`, отдельного типа нет |
| `movers` — Грузчики | 💪 | бригада, чел. | — |
| `tow` — Эвакуатор | 🛻 | тип погрузки (ломаная платформа / паук), макс. тоннаж (до 3.5 / до 8 / 20+ т) | пороги тоннажа — дефолт, владелец подтвердит |
| `bucket_lift` — Автовышка (жираф) | 🏗️ | рабочая высота (8–60 м), тип стрелы (телескоп / коленчатая) | ≠ манипулятор (КМУ, груз крюком — будет отдельным типом) |

## 4. i18n — конвенция ключей

Все в `ka/ru/en` (`src/config/i18n.js`):

```
svc_<type>                      — название типа        («Эвакуатор»)
svc_<type>_<fieldKey>           — подпись поля          («Тип погрузки»)
svc_<type>_<fieldKey>_<value>   — подпись варианта enum («Паук (частичная погрузка)»)
service_desc_<type>_body        — описание в блоке «услуги» на главной
chip_<type>                     — чип «что нужно сделать» (только tow/bucket_lift; у van/movers свои chip_move/chip_movers)
```

Если ключа варианта enum нет — фолбэк на `value + unit` (напр. тоннаж `«8 т»`), поэтому
для числовых enum-опций подписи необязательны.

---

## 5. Как добавить новый тип (напр. `manipulator` — КМУ)

1. Блок в `SERVICE_TYPES` (`src/config/serviceTypes.js`) + добавить в `SERVICE_TYPE_ORDER`.
2. Строки `svc_manipulator*` + `service_desc_manipulator_body` + `chip_manipulator` в
   `i18n.js` (ka/ru/en).
3. **Всё.** Форма, каталог, фильтры, главная подхватят автоматически.
   Рассылка/админка — когда будут переведены на конфиг (Фазы 4–5).

Миграций БД не требуется — `attributes` это JSONB.

## 6. Статус по фазам (2026-09-06)

| Фаза | Что | Статус |
|---|---|---|
| 1 | Схема (`cities`, `districts`, `master_services`, `*.city_id`), конфиг, миграция существующих | ✅ |
| 2 | Форма `/join` из конфига: тип → поля + город + районы + фото | ✅ |
| 3 | Каталог + главная из конфига, спецтехника видна, группа `junk` убрана | ✅ |
| 4 | Рассылка: кнопки модератора из конфига, матчинг-движок по `attributes`, форма заявки клиента (тип+город+район) | — |
| 5 | Админка из конфига; удалить старые колонки `category`/`vehicle_size`/`is_flatbed` | — |

**Что работает сейчас:** регистрация всех 4 типов; каталог показывает группы (появляются,
когда есть одобренный исполнитель); прямой звонок из каталога (платное раскрытие номера)
для любого типа; главная рекламирует все 4 услуги.

**Что НЕ работает до Фазы 4:** заявка клиента через композер на спецтехнику доходит до
модератора **текстом**, но авто-рассылки нет — в Telegram у модератора кнопки только
`transport` / `movers` / `junk` / `flatbed` + размеры. Модератор обрабатывает эвакуатор
вручную.

**Переходный дуализм (до Фазы 5):** `van`/`movers` при регистрации пишут И
`master_services`, И старые колонки `masters.category`/`vehicle_size`/`is_flatbed` — их
ещё читает рассылка (`order.service.notifyMasters`). Для `tow`/`bucket_lift` старого
эквивалента нет: `category` = сам тип, старый каталог/рассылка их игнорируют.

## 7. Открытые вопросы

- **Пороги тоннажа эвакуатора** (3.5 / 8 / 20 т) и **высоты жирафа** (свободный ввод
  8–60 м) — мои дефолты в `serviceTypes.js`, владелец обещал сверить с рынком.
- **Грузинские `svc_*` / `service_desc_*` строки** — писал не носитель, нужна вычитка
  (как и юр.текст, см. `docs/consent-and-legal.md`). `ავტოამწე` для автовышки — вариант.
- **Выбор машины из готового списка** (Газель / Спринтер / Транзит → тир+кузов) как
  альтернатива вводу габаритов — обсуждалось, список под тбилисский парк не составлен.
- **Мультиуслуга** (один исполнитель — несколько типов): таблица `master_services` это
  поддерживает, но регистрация и кабинет заводят/показывают одну.
- **Города кроме Тбилиси**: `cities` заполнена (Батуми/Кутаиси/Рустави, `is_active=false`),
  включаются флагом — но каталог/рассылка ещё не city-aware (Фаза 4).
- Мелкая SEO-копия (`coverage_body`, часть FAQ) ещё говорит про «вывоз мусора» как
  отдельную услугу — не ломает, обновить при случае.

## 8. pg-mem — чего избегать в SQL этой подсистемы

(полный список — `HANDOFF.md` + память `xtender-db-test-harness`)

- **Нет `jsonb_build_object`** — JSON собирать конкатенацией строк + `::jsonb`.
- **Коррелированный `NOT EXISTS` в `INSERT … SELECT`** падает — идемпотентность через
  `UNIQUE` + `ON CONFLICT DO NOTHING`.
- **`GROUP BY` по jsonb-колонке** — не полагаться; `listMasters` поэтому клеит attributes
  в JS вторым запросом, а не джойном.
- Хранение/чтение JSONB как таковое — работает (возвращается распарсенным объектом).
