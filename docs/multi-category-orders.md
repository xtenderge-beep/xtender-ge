# Заявка из нескольких категорий

Реальный сценарий: клиенту нужен переезд — грузчики **и** машина. Модератор
рассылает заявку двум группам исполнителей. Клиент нашёл грузчиков, но машина
ещё нужна — раньше закрыть можно было только всю заявку сразу.

Документ описывает, как это устроено после работ **18.09.2026**
(коммиты `c843f74`, `d2fa1c4`, `aeff293`, `c576a8c`): закрытие по
категориям, воронка по группам исполнителей, экран клиента. В конце —
предложение по кабинету заказчика, которое **не реализовано** и ждёт решений
владельца (там же — что сознательно не делаем и почему).

Оперативный статус и открытые вопросы — [tasks.md](tasks.md); архитектурный
снимок — [current-state.md](current-state.md).

---

## 1. Как заявка попадает в несколько категорий

- `orders.target_categories TEXT[]` — растёт по мере рассылки: каждый запуск
  `dispatch.service.dispatch` добавляет категорию (`order.service.addTargetCategories`).
  Заявка уходит категориям **по очереди**, а не одним действием.
- `order_dispatches (order_id, category, vehicle_size, language)` с уникальным индексом на все
  четыре колонки — защита от повторной рассылки той же группе. `language` — кому направлена
  рассылка: пусто — всем, иначе код языка ([dispatch-by-language.md](dispatch-by-language.md)).
- `dispatch_runs` / `dispatch_deliveries` — кому именно ушёл лид
  (`status='accepted'` — доставлено и списано). Пишутся с 13.09.2026.
- `order_views (order_id, master_id, event_type)` — клики мастера по заявке
  (`view` / `call` / `whatsapp`), уникальны по тройке.

**Ловушка с ключами категорий.** Ключи в `target_categories`, `order_dispatches`
и `masters.category` — `movers`, `transport`, …, а строка справочника
(`service_categories`) для той же категории называется по slug: `van`
(`category.service.toCategory`: `van → transport`). `flatbed` («Бортовые») —
не строка справочника и не `masters.category`, а подвыборка `transport`
(`masters.is_flatbed`, см. `order.service.dispatchFilter`). Любой код, который
сопоставляет ключ заявки с названием, обязан идти через
`category.service.labelMap(lang)` — иначе клиент увидит сырое `transport`
(так и было на боевой странице до `c576a8c`).

## 2. Закрытие по категориям

Таблица `order_category_closures (order_id, category, closed_at, closed_by,
reason)`, `PRIMARY KEY (order_id, category)` — одна строка на закрытую
категорию (`CREATE TABLE IF NOT EXISTS`, накатывается со `schema.sql` на
старте, данных не мигрирует).

`order.service.closeOrderCategory(token, category, { actor, reason, meta })`:

| Ситуация | Результат |
|---|---|
| заявки нет | `null` |
| заявка уже закрыта / категории нет в `target_categories` / категория уже закрыта | тихий no-op, возвращается заявка как есть, в журнал ничего не пишется |
| закрываемая категория **не последняя** открытая | строка в `order_category_closures`; `orders.status` **не меняется**; в `sms_consent_logs` — `ORDER_CATEGORY_CLOSED` (`metadata.category`, `remaining_categories`) и, если закрывает клиент, `CONTACT_SHARING_WITHDRAWN` со `scope='category:<ключ>'` |
| закрываемая — **последняя** открытая | заявка закрывается целиком тем же кодом, что и раньше (`finalizeClose`): `status='closed'`, `ORDER_CLOSED` один раз, для клиента — `CONTACT_SHARING_WITHDRAWN` со `scope='this_order'` |

Следствия:
- Последняя категория закрывается через `orders.status`, а не строкой в
  `order_category_closures`, поэтому `getClosedCategories` её не возвращает.
- Весь прежний код, который читает `orders.status`, не менялся: заявка с
  одной категорией и ещё не разосланная работают ровно как раньше.
- Закрывает целиком заявку тот же `finalizeClose`, что и `closeOrder`
  (клиентский `/close`, модераторский `/close`).
- Приглашение оценить исполнителя (SMS `/review/<ownerToken>`) уходит только
  когда заявка закрылась **целиком**; при частичном закрытии рано.

Маршруты (копии существующих `/close`):
- клиент — `POST /api/orders/:token/close-category`, тело `{category, reason}`,
  доступ по куке владельца; `reason ∈ {found_provider, no_longer_needed}`;
  категория обязана входить в `target_categories` (иначе 400);
- модератор — `POST /admin/orders/:token/close-category`, CSRF,
  `reason='admin_closed'`, SMS клиенту не отправляется.

Оба вызывают `telegramService.updateMessage`, поэтому сообщение модератору
в Telegram обновляется сразу.

### Рассылка в закрытую категорию запрещена

`dispatch.service.preview` (а значит и `dispatch`) отказывает с
«Эта категория заявки уже закрыта». Без этого была дыра: уникальный ключ
`order_dispatches` включает размер транспорта и язык рассылки, поэтому после закрытия
`transport` можно было запустить `transport/XL` после `transport/L`, и
исполнители уже закрытой категории получили бы **платный** лид по заявке,
которую для них закрыли. Закрытые категории также скрыты из формы рассылки в
`admin/order-detail.ejs`.

## 3. Что видит каждый участник

**Клиент** (`/order/:token`, `/o/:ownerToken`, `order.ejs`). Если открытых
категорий больше одной: заголовок «Ваша заявка отправлена в несколько
категорий. Что закрыть?», кнопки «Закрыть только: <категория>», подсказка
«Остальные категории продолжат получать вашу заявку» и отдельная
«Закрыть всю заявку». Список причин («Нашёл исполнителя» / «Услуга больше не
нужна») один и действует для любой кнопки. Осталась одна открытая категория —
прежний единый экран с одной кнопкой. Тексты: `order_close_which`,
`btn_close_only`, `order_close_rest_hint`, `btn_close_all_categories` (ru/ka/en).

**Исполнитель.** Открывает лид по `?master=<id>` — страница учитывает **его**
категорию: если закрыта именно она, показывается «эта часть заявки уже
закрыта», даже когда для другой категории заявка ещё активна
(`masterCategory`, `order_closed_notice_category`). То же в кабинете «мои
заявки» (`master.service.getMasterLeads(masterId, masterCategory)` — join на
`order_category_closures`).

**Модератор.** `/admin/orders/:token`: кнопки закрытия по категориям и целиком,
закрытые категории помечены в блоке «Рассылка по категориям», воронка по
группам (§4). В Telegram-сообщении — та же воронка, закрытые группы с 🔒.

**Не менялось:** список «Мои заявки» (`/my-orders`) и шапка Telegram-сообщения
показывают только общий статус заявки — точная картина по категориям видна на
странице заявки и в админке.

## 4. Воронка по группам исполнителей

Раньше воронка (`order_views`) была одна на всю заявку — было не понять, какая
группа откликается. `order.service.getOrderFunnelByCategory(orderId)` считает
на каждую группу (`masters.category`):

- `received` — мастера, которым лид реально ушёл: `dispatch_deliveries.status='accepted'`;
  для заявок до 13.09.2026 (доставки не писались) — списание `lead_charge` в
  `balance_transactions`. Объединение по мастеру без дублей;
- `view` / `call` / `whatsapp` — уникальные мастера (`order_views` уже уникален);
- `contacted` — **отклик**: мастер нажал «Позвонить» **или** WhatsApp (уникальные
  мастера из `call ∪ whatsapp`). Просмотр откликом не считается — как и в
  `crmMetrics`. Доля отклика — от `received`.

Детали:
- Группа, в которую разослали, но лид никто не получил (не хватило баланса),
  остаётся в отчёте нулями, а не пропадает.
- `flatbed` в разрезе учитывается как `transport` (это подвыборка, см. §1).
- Агрегация в JS, не в SQL: `COUNT(DISTINCT)`/`FILTER` на pg-mem (dev-server)
  ненадёжны.
- Группа определяется **текущей** `masters.category` мастера: если категорию
  сменили после рассылки, его цифры перейдут в новую группу.
- «Отклик» — это **нажатие кнопки**, а не подтверждённый разговор. В любых
  клиентских текстах писать «откликнулись», не «связались».

Где показывается: сообщение модератору в Telegram (`telegram.buildMessageText`,
блок «Воронка по группам» + «Всего»; при сбое запроса — прежняя общая воронка)
и `/admin/orders/:token`. Клиентская страница и «Мои заявки» **не менялись** —
клиент видит прежние общие цифры. Каждый клик мастера вызывает `updateMessage`,
поэтому цифры в Telegram живые (старые сообщения обновятся при ближайшем клике).

```
📊 Воронка по группам:
💪 Грузчики 🔒 закрыта: получили 12 · 👀 5 · 📞 2 · 💬 3 · отклик 4 из 12 (33%)
🚚 Перевозки: получили 8 · 👀 1 · 📞 0 · 💬 0 · отклик 0 из 8 (0%)

Всего: 👀 6 · 📞 2 · 💬 3
```

## 5. Грабли, на которые уже наступили

- **Иконка не рисуется.** Публичные страницы грузят не полный Font Awesome, а
  мини-подмножество `public/fa/` (собирается `scripts/build-fa.js`). Иконка,
  добавленная в шаблон, но не внесённая в `ICONS`, молча не отображается —
  так пропали ✕ на кнопках закрытия и стрелка на `/join`. Правило: новая иконка
  в публичном шаблоне = строка в `ICONS` + `npm run build:fa`. Ловит
  `tests/fa-subset.test.js` (админка `views/admin` грузит только `app.css` без
  `fa.css` — её иконки не проверяются).
- **Подпись категории.** См. §1 — только через `category.service.labelMap`.
- **Проверять текст на странице в тестах** нужно как содержимое тега
  (`>текст<`): строки переводов встроены ещё и в `<script>` (`clientStrings`),
  простой `includes` даёт ложные срабатывания.

## 6. Тесты

  закрытие, область журнала согласия, закрытие модератором, заявка с одной

и откат, а не настоящая блокировка: `SELECT … FOR UPDATE` в
`closeOrderCategory` на реальном PostgreSQL отдельно не проверялся.

## 7. Выкладка

- Миграция: только идемпотентный `CREATE TABLE IF NOT EXISTS order_category_closures`
  на старте; данные не пересчитываются.
- Изменились статические файлы `public/fa/` (шрифт иконок) — должны попасть на
  сервер вместе с кодом.
- Railway деплоит после push в `main`; успешный push деплой не подтверждает —
  статус смотреть отдельно.

## 8. Известные ограничения

- Модератор рассылает категории по очереди. Если клиент закроет **единственную**
  уже разосланную категорию до рассылки во вторую, заявка закроется целиком
  (единственная открытая категория = полное закрытие), и во вторую категорию
  разослать уже не получится.
- «Мои заявки» и шапка Telegram-сообщения не показывают состояние по категориям.
- Нет «переоткрыть категорию» ни у клиента, ни у модератора.
- Закрытие категории `flatbed` не помечает строку `transport` как закрытую в
  воронке (в разрезе они одна группа).
- `POST /api/orders/:token/log-view` принимает `masterId` от клиента без
  проверки (так было и раньше) — цифры воронки можно исказить.
- Грузинские строки экрана закрытия (`order_close_which`, `btn_close_only`,
  `order_close_rest_hint`) написаны без вычитки носителем языка.

## 9. Предложение (не реализовано): кабинет заказчика

Обсуждено 18.09.2026. Владелец явно: **новые идеи не внедрять**, запушить
только уже сделанное. Оформлено как задача `[!]` в [tasks.md](tasks.md) с
вопросами владельцу. Ниже — суть, чтобы решение можно было принять и не
переизобретать.

**Как сейчас.** Доступ без аккаунтов: SMS-ссылка `/o/<ownerToken>` (работает
на любом устройстве) и кука; `/my-orders` показывает только заявки,
запомненные **этим браузером** (карточка: номер вроде `#RI5GIC`, статус, две
строки текста, дата). Править заявку клиент может только в одном случае:
модератор вернул её на уточнение (`needs_revision`) — тогда меняются текст и
район и заявка возвращается в `pending_review` (`orderRevision.service.resubmit`,
защита от гонки — `revision_version`). Фото и категории клиент не меняет,
категории добавляет только модератор. Опечатку после отправки исправить нельзя.

**Главное правило.** Что можно менять — зависит от того, ушла ли заявка
исполнителям: после рассылки они уже заплатили за лид с этим текстом, поэтому
переписывать его нельзя; до рассылки — можно, но только через модератора.

| Этап | Что доступно клиенту |
|---|---|
| На проверке (не разослана) | Изменить текст, район, фото; заявка возвращается модератору (исполнители ещё не платили; гонку с рассылкой держит `revision_version`) |
| Вернули на уточнение | Исправить и отправить снова (уже есть) |
| Разослана | **Дополнить** (дописать деталь, исходный текст не переписывается); **Добавить услугу** («нужна ещё машина») — задача модератору, рассылка новой категории платная и идёт через него; закрытие по категориям / целиком (есть) |
| Закрыта | Оценить исполнителя; **Повторить заявку** (форма заполняется заранее) |

Если задача изменилась по сути — «Создать новую заявку на основе этой»: идёт
через модератора как обычная, исполнители платят только за реально новый лид.

**Карточка «Моих заявок».** Вместо номера — название «Переезд · район»;
статус словами; по каждой категории своя строка (например, «откликнулись: 3»)
со своей кнопкой; одна главная кнопка на состояние. Только реальные числа, без
выдуманных сроков вроде «проверим за 5 минут» (срок можно показывать, только
если он считается из данных).

**Ограничения, которые нужно сохранить.**
- «Повторить заявку» заполняет форму, но **не пропускает согласие и
  подтверждение номера**: журнал согласий ведётся на каждую заявку.
- Правки и дополнения — события в `sms_consent_logs` (по аналогии с
  `ORDER_RESUBMITTED`).
- В клиентских текстах — «откликнулись», а не «связались» (§4).

**Чего не делать.** Правку текста после рассылки (исполнители заплатили);
автоматическое добавление категории без модератора (рассылка стоит денег).

**Порядок работ.** (1) карточки, «Изменить» до рассылки, «Повторить заявку»;
(2) «Дополнить» и «Добавить услугу»; (3) вход по номеру с кодом из SMS, чтобы
видеть заявки с любого устройства (код и журнал согласий уже есть; каждый вход
стоит SMS).

**Открытые вопросы владельцу** — в [tasks.md](tasks.md).
