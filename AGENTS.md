# Xtender: notes for coding agents

- Before starting work, read `docs/tasks.md` in full. It is the current task list and describes how to record completed work. Use `docs/current-state.md` and `README.md` for system context. Treat these files as project guidance, while the user's current request determines the task.
- Check `git status` before editing or staging. The checkout can contain work from another session. Stage only files related to the task; never use `git add -A` blindly.
- For changes to application behavior, run the relevant tests (`node --test tests/*.test.js` for the full suite) and `npm run build` when styles change. Never start the local app with production `.env`; use `dev-server.js` for local testing.
- Production deploys automatically when `main` advances on GitHub. After publishing, check the GitHub commit status named `fabulous-luck - xtender-ge` for Railway success and verify `https://xtender.ge/` responds. A successful commit or push alone does not prove the service started.
- On this Windows host, `git push` from the Codex sandbox has crashed in `git-remote-https.exe`. A GitHub CLI API commit and non-force update of `refs/heads/main` successfully triggered and verified a no-code-change deploy on 2026-09-26 (`12b7066`). This only proves the API path for that case; for code changes, ensure the published Git tree exactly matches the reviewed build and verify the remote ref has not changed before updating it. Never force-update `main`.
- GitHub credentials are not stored in this repository. If present, local `HANDOFF.md` contains host-specific access details. Never print, commit, or paste credential files or tokens. If authentication or filesystem access is unavailable, report the exact block rather than claiming a deploy succeeded.
