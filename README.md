# Xtender

Сервис-маркетплейс для заказа услуг по районам Тбилиси: перевозки/машины, грузчики, вывоз мусора. Клиент публикует заявку текстом, модератор вручную распределяет её по категориям исполнителей через Telegram, исполнители получают SMS со ссылкой на заявку.

Прод: **https://xtender.ge**

## Как это работает

1. Клиент на главной странице описывает задачу текстом и жмёт «Опубликовать».
2. Указывает телефон → получает SMS с 4-значным кодом и короткой ссылкой на свою заявку (`/o/<owner_token>`).
3. Вводит код → заявка подтверждается и уходит **модератору в Telegram-бот** с кнопками категорий (Машины/Грузчики/Вывоз мусора/Бортовые, машины дополнительно по размеру L/XL/XXL).
4. Модератор нажимает нужные категории (можно несколько) → активным мастерам этой категории уходит SMS со ссылкой на заявку (`/order/<token>`) → сообщение модератора в Telegram обновляется на месте: статус, кто получил рассылку, воронка кликов.
5. Мастер открывает ссылку → видит заявку → «Позвонить» / WhatsApp — клики логируются и обновляют воронку в Telegram-сообщении.
6. Клиент в любой момент может открыть свою ссылку (`/o/...`, работает без кук/с любого устройства) и закрыть заявку — сообщение в Telegram обновится на «🔒 закрыта», новые мастера по старым ссылкам увидят, что заявка уже занята.

Отдельно есть каталог исполнителей на главной странице (фильтр по категории/размеру) — клиент может звонить напрямую в обход модерации.

### Регистрация исполнителей и баланс

Исполнители регистрируются сами на `/join` (форма на 3 языках, с OTP-подтверждением телефона — как у клиента, но отдельным Redis-неймспейсом, см. `otp.service.js`). Категории при регистрации — только «Разнорабочий» (`movers`) и «Водитель с машиной» (`transport`). Для водителя форма собирает реальные габариты кузова (длина/ширина/высота, см) и тип кузова (закрытый/борт) — на сервере это склеивается в текстовое поле `vehicle_type` (например «Ford Transit, 400×180×200 см, закрытый кузов»); отдельный размерный класс (L/XL/XXL) при самостоятельной регистрации больше не спрашивается и `vehicle_size` остаётся `NULL`, из-за чего такой мастер попадает во **все** размерные рассылки категории «Машины» (это уже штатное поведение `notifyMasters` — `vehicle_size IS NULL` считается «любой размер»). Форма требует явного согласия на получение SMS-уведомлений (чекбокс + ссылка на `/terms`) — момент согласия фиксируется в `masters.terms_accepted_at`. Новый мастер создаётся с `is_active = false` и уходит модератору в Telegram с кнопкой «✅ Одобрить» — только после этого он появляется в каталоге и в рассылке.

Два канала монетизации, оба настраиваются в `/admin/settings` (`app_settings`), с независимыми ценами (подробно, включая связь с офертой и отсутствие индивидуальных цен по исполнителям — **[docs/pricing-and-monetization.md](docs/pricing-and-monetization.md)**):
1. **Лид с рассылки** — каждое SMS/Telegram-уведомление о заявке списывается с баланса мастера (`masters.balance_tetri`, в тетри — 1 GEL = 100 тетри), сейчас **50 тетри** (0.50 GEL, `app_settings.lead_price_tetri`). За сам факт отправки уведомления, не за исход (звонок/ответ клиенту не проверяется). Если баланса не хватает — мастера просто пропускают при рассылке (без ухода в минус).
2. **Показ номера в каталоге** — клиент, который не подаёт заявку, а сам находит исполнителя в каталоге на главной, подтверждает свой телефон SMS-кодом (purpose `'catalog'`, отдельная OTP-сессия от подачи заявки; подтверждение «запоминается» httpOnly-кукой `catalog_verified` на 24ч) и жмёт «Показать номер» — с баланса исполнителя списывается `app_settings.catalog_call_price_tetri` (по умолчанию тоже 50 тетри), номер показывается и подставляется в кнопки звонка/WhatsApp. Дедуп: повторный показ того же мастера тому же звонящему в течение 24ч не списывает повторно (`master.service.js` `revealPhoneForCall`). Если баланса не хватает — кнопки нет вообще. Сырой номер и баланс никогда не попадают в HTML каталога или в `GET /api/masters` JSON — иначе платный gate обходится просмотром исходника/curl.

Пополнение баланса — вручную: исполнитель переводит деньги (минимум 5 GEL) по договорённости, модератор подтверждает командой прямо в Telegram-боте:

```
/topup +995599112233 10
```
(номер телефона + сумма в GEL — зачислится на баланс этого мастера). Никакого онлайн-эквайринга нет.

Удобнее — через кнопки внизу чата бота: «💰 Пополнить баланс» и «🔍 Проверить баланс» запускают пошаговый диалог (бот сам спрашивает номер телефона, потом сумму). Кнопки появляются после отправки `/menu` боту один раз. Состояние диалога хранится в Redis (`admin_flow:<chat_id>`, TTL 5 минут).

Сразу после регистрации исполнитель получает SMS с личной ссылкой `/master/<master_token>` (без пароля, по аналогии с `/o/<owner_token>` у клиента) — там в любой момент видно статус (на модерации / активен) и текущий баланс.

## Стек

- Node.js + Express 4, шаблоны — EJS (`src/views`)
- PostgreSQL (`pg`) — основное хранилище
- Redis (`ioredis`) — OTP-коды, лимиты по частоте отправки
- Telegram Bot API — модерация заявок (обычные HTTP-запросы через `axios`, без SDK)
- Свой SMS-шлюз (HTTP GET) — код подтверждения и рассылка мастерам
- Multer — загрузка фото/PDF к заявке
- Railway — хостинг и автодеплой, Cloudflare — домен

## Локальная разработка

```
node dev-server.js
```

Поднимает сервер на `localhost:3000` с **in-memory** Postgres (`pg-mem`) и Redis (`ioredis-mock`) — реальная БД не нужна, SMS не отправляются (пишутся в консоль). Автоматически сеет 50 демо-мастеров при старте.

**Никогда не запускайте `npm start` / `node src/app.js` локально** — `.env` содержит настоящие продовые ключи (SMS-шлюз, Telegram-бот), реальные SMS могут уйти по реальным номерам, а приложение подключится к продовой базе.

Известные ограничения `pg-mem` (если правите SQL-миграции — проверяйте на реальной Postgres тоже):
- не поддерживает `ANY($1::uuid[])` на UUID-массивах
- не поддерживает коррелированные подзапросы
- `ON CONFLICT DO NOTHING RETURNING *` возвращает существующую строку вместо пустой
- падает при повторном прогоне DDL через `Pool.query()` на некоторых constraint'ах — поэтому `dev-server.js` выставляет `SKIP_DB_MIGRATIONS=1` и накатывает схему сам через нативный API `pg-mem`
- не поддерживает plpgsql-функции, `DO`-блоки, триггеры, `RULE` — такой DDL живёт в отдельном `schema.postgres.sql` (накатывается только на реальной Postgres, после `schema.sql`)

| `SMS_GATEWAY_URL` | адрес SMS-шлюза (необязательно, есть дефолт в коде) |

| `SMS_GATEWAY_PASSWORD` | пароль SMS-шлюза |
| `TELEGRAM_BOT_TOKEN` | токен бота-модератора (`@xtendergebot`) |
| `TELEGRAM_MODERATOR_CHAT_ID` | chat_id, куда шлются заявки на модерацию |
| `TELEGRAM_WEBHOOK_SECRET` | секрет для проверки заголовка `X-Telegram-Bot-Api-Secret-Token` на `/api/telegram/webhook`. Установлен в проде и подтверждён (без заголовка/с неверным — 401). Приложение само переустанавливает вебхук с этим секретом при каждом старте (`telegramService.setWebhook()` в `app.js`) |
| `NODE_ENV` | `development` включает dev-режимы (SMS/Telegram не отправляются по-настоящему) |
| `SKIP_DB_MIGRATIONS` | пропустить авто-накат `schema.sql` + `schema.postgres.sql` при старте (нужно только `dev-server.js`) |
| `CONSENT_HASH_PEPPER` | необязательная «перчинка» к SHA-256 OTP-кода в `sms_consent_logs` — без неё 4-значный код перебирается по дампу БД за 10k хэшей. Пусто = чистый SHA-256 |

Полный список с пустыми значениями — в `.env.example`.

## База данных

Схема живёт в `schema.sql` (+ `schema.postgres.sql` для триггеров/функций, которые не тянет pg-mem) и накатывается автоматически при каждом запуске (`runMigrations()` в `app.js`), включая прод — миграции идемпотентны (`CREATE TABLE IF NOT EXISTS` + отдельные `ALTER TABLE ADD COLUMN IF NOT EXISTS` для полей, добавленных позже).

Основные таблицы:
- **masters** — каталог исполнителей: категория, тип/размер машины, цена, телефон, активность, подписка, `balance_tetri` (баланс в тетри), `master_token` (личная ссылка), `terms_accepted_at` (момент согласия). `price_text` — поле есть в схеме (заполнено у демо-мастеров), но форма `/join` его больше не собирает
- **orders** — заявки: описание, район, статус (`unverified` → `pending_review` → `closed`), `token` (для мастеров) и `owner_token` (для клиента) — два независимых коротких (10 символов) идентификатора, чтобы мастер не мог подделать доступ владельца
- **order_dispatches** — какой категории (и размера) уже отправлена рассылка по заявке — защита от повторных SMS
- **order_views** — клики мастеров по заявке (переход/звонок/WhatsApp) — данные для воронки
- **order_files** — вложения к заявке (фото/PDF)
- **sms_consent_logs** — журнал согласий на SMS (Double Opt-In) и доставок: строка на каждое подтверждение OTP (`CONSENT_SMS_OTP_VERIFIED` для `/join` + `AUTH_/ORDER_/REVIEW_SMS_OTP_VERIFIED`) с IP/User-Agent/версией оферты/текстом согласия, и строка на каждую отправленную транзакционную SMS (`SMS_OTP_SENT`, `LEAD_SMS_SENT`, `TX_SMS_SENT`). Append-only (только INSERT; на реальной Postgres закреплено триггером), без FK — переживает удаление профиля/заявки. Код SMS хранится только как SHA-256. **Подробно: [docs/consent-and-legal.md](docs/consent-and-legal.md)**
- **app_settings** — key/value настройки приложения, правятся в `/admin/settings`: `lead_price_tetri` (цена лида с рассылки), `catalog_call_price_tetri` (цена показа номера в каталоге)
- **districts / master_districts** — районы (задел на будущее, сейчас не в основном флоу)

## API

Все — `/api/...`, ответы `{ success: boolean, ... }`.

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/otp/send` | создаёт заявку в статусе `unverified`, шлёт SMS с кодом + ссылкой |
| POST | `/api/otp/verify` | проверяет код, помечает телефон как verified в Redis (10 мин) |
| POST | `/api/orders` | активирует заявку (нужен verified-телефон), прикрепляет файлы, уведомляет модератора в Telegram |
| POST | `/api/orders/:token/close` | закрывает заявку (владелец, по cookie) |
| POST | `/api/orders/:token/log-view` | логирует клик мастера (view/call/whatsapp) |
| GET | `/api/masters?category=` | список активных мастеров, опционально по категории — без `phone`/`balance_tetri` (см. раскрытие номера ниже) |
| POST | `/api/masters/otp/send` | OTP для регистрации исполнителя (отдельный namespace от клиентского) |
| POST | `/api/masters/otp/verify` | подтверждение телефона исполнителя |
| POST | `/api/masters/register` | создаёт мастера (`is_active=false`), уведомляет модератора в Telegram |
| POST | `/api/catalog/otp/send` | OTP для клиента, который хочет увидеть номер мастера в каталоге (purpose `'catalog'`) |
| POST | `/api/catalog/otp/verify` | подтверждает телефон звонящего, ставит куку `catalog_verified` на 24ч |
| POST | `/api/masters/:id/reveal-phone` | платно раскрывает номер мастера (нужна кука `catalog_verified`); без неё — `{needsVerification:true}` |
| POST | `/api/reviews/request-code` | отзыв из каталога: шлёт OTP на телефон (purpose `review`) |
| POST | `/api/reviews/verify` | проверяет код + говорит, может ли этот номер оценить этого мастера (`eligible` / `already_reviewed` / `not_eligible`) |
| POST | `/api/reviews` | сохраняет отзыв в очередь модерации. Принимает `{ownerToken,…}` (флоу по SMS-ссылке `/review/<owner_token>`) или `{phone,…}` (флоу из каталога, телефон должен быть verified) |
| POST | `/api/telegram/webhook` | приём callback/текстовых команд от модератора (диспетчеризация, одобрение мастера, `/topup`); защищён `TELEGRAM_WEBHOOK_SECRET` |

Плюс серверные HTML-страницы: `/` (главная), `/join` (регистрация исполнителя), `/terms` (Публичная оферта) + `/privacy` (Политика конфиденциальности) — обе `v1.2-2026-09-03`, `/master/:token` (баланс исполнителя), `/order/:token`, `/o/:ownerToken`, `/my-orders`, `/lang/:code`. Все — ka/ru/en с префиксом локали. Реквизиты юр. лица — из `SERVICE_REQUISITES` в `src/config/legal.js` (`entityName/idCode/legalAddress` пока `null` → «уточняется…»). Как править текст оферты/политики, версии и реквизиты — **[docs/consent-and-legal.md](docs/consent-and-legal.md)**.

Админка (`/admin/*`, вход по `ADMIN_PASSWORD`): обзор, специалисты, заявки, отзывы, поддержка, промокоды, менеджеры, **`/admin/consent`** — журнал согласий на SMS: поиск по номеру, карточка Double Opt-In, кнопка «Скачать JSON» (`/admin/consent/export?phone=` — тот же отчёт, что у `scripts/export-consent-log.js`). Ссылка на журнал по номеру есть и в карточке специалиста.

## Деплой

Railway, автодеплой при `git push` в `main` (репозиторий `xtenderge-beep/xtender-ge`). Домен `xtender.ge` подключён через Cloudflare. Проект в Railway называется `fabulous-luck`, сервисы: Postgres, Redis, `xtender-ge` (само приложение).

Никакого отдельного шага "собрать/задеплоить" не требуется — пуш в `main` = деплой.

## Безопасность

`/admin` — пароль + HMAC-подписанная сессия + CSRF + rate-limit (по IP и общий) +
Telegram-алерт на каждый вход и на срабатывание rate-limit. Разбор находок,
что исправлено и что ещё нет (2FA, отзыв сессий, `npm audit`) — **[docs/security-audit.md](docs/security-audit.md)**.

## Известные ограничения

- Нет живых обновлений без перезагрузки страницы (обычные серверные страницы, без WebSocket)
- Используемый SMS-шлюз сам дописывает служебную строку к тексту SMS (например `NO XTENDER-94710`) — в API шлюза нет параметра для имени отправителя, разбираемся с провайдером шлюза
- SMS-шлюз работает по `http://`, не `https://` — креды и текст сообщения идут в незашифрованном виде
- Мастерам, уже проявившим интерес к заявке, не приходит SMS при её закрытии клиентом (осознанное решение)
